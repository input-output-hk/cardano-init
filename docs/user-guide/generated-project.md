# The generated project

A typical project (on-chain + off-chain + devnet) looks like this:

```text
my-protocol/
├── Justfile        # top-level build / test / clean
├── README.md       # how to work with this specific stack
├── AGENTS.md       # brief for coding agents
├── CLAUDE.md       # imports AGENTS.md
├── .gitignore
├── .env            # shared connection details
├── .mcp.json       # MCP servers for coding agents
├── blueprint/      # CIP-57 blueprint, written by on-chain `build`
├── spec/           # protocol specification in plain Markdown
├── on-chain/       # validators + their own Justfile
├── off-chain/      # transaction building + its own Justfile
└── devnet/         # local chain + its own Justfile
```

Only the roles you select get a directory. Add `--nix` to also get a `flake.nix` and `.envrc` that pin the project's toolchains. Add `--dry-run` to see the full file list without writing anything.

## The Justfile workflow

Every component has its own `Justfile` and works on its own. The top-level `Justfile` runs the tasks that finish and can be combined:

| Target | What it does |
|--------|--------------|
| `just build` | Builds every component. On-chain builds first, so `blueprint/plutus.json` exists for the other components. |
| `just test` | Builds the on-chain blueprint, then runs each component's tests (including formal verification, if selected). |
| `just clean` | Removes build artifacts from every component. |

There are also targets for each role, such as `just build-on-chain` and `just test-off-chain`. Run `just` with no arguments to list them.

### Long-running tasks: `dev`

Tasks that keep running (watch modes, local devnets, service stacks) belong to **one component**, and the top-level `Justfile` does not run them. A component has a `dev` target only when it has such a task. Run it from the component's `Justfile`:

```bash
just -f devnet/Justfile dev
just -f infra/Justfile dev
just -f <dir>/Justfile --list   # see what a component offers
```

## `blueprint/`

The on-chain component's `build` writes the compiled validators to `blueprint/plutus.json`, a [CIP-57](https://cips.cardano.org/cip/CIP-0057) blueprint. The off-chain code reads the compiled scripts from this file and applies its parameters. See [The interface contract](how-it-works.md#the-interface-contract).

## `spec/`

`spec/` describes what your protocol does and why it is safe. Write the design here before implementing a change, then review the code against it. The files are plain Markdown; nothing in this folder is built or executed.

- `spec/README.md` explains the conventions for documenting actors, assets, validators, transactions, and invariants.
- `spec/giftcard.md` specifies the worked example. It is generated only when you select an on-chain, off-chain, or fullstack component. Projects without those components get the README alone.

The folder is generated by default. Pass [`--no-spec`](commands.md#create-a-project) to skip it in one-shot or JSON mode. Interactive setup asks whether to include it, with **Yes** as the default.

Keep the specification in step with your code. The folder is yours after generation: `add` and `remove` never rewrite or delete it. Machine-checked specifications belong in the formal-methods component instead.

## `.env`

`.env` holds the chain connection details for all components:

```bash
CARDANO_NETWORK=preview

INDEXER_URL=
INDEXER_PORT=
NODE_SOCKET_PATH=
OGMIOS_URL=
TX_SUBMIT_URL=
DOLOS_GRPC_URL=
CARDANO_NODE_API_URL=
```

The values start empty. A component that starts a local endpoint (a devnet such as Yaci DevKit, or an [infrastructure provider](infrastructure.md)) fills them in during its `dev` task. When a value is empty, the components that read it keep working, for example by connecting to a public provider.

## `AGENTS.md`

Every project includes an `AGENTS.md`, and a `CLAUDE.md` that imports it, written for the tools you selected. See [For coding agents](agents.md#generated-agentsmd) for what it contains.

## `.mcp.json`

`.mcp.json` lists the [MCP](https://modelcontextprotocol.io) servers a coding agent can use in this project. Claude Code reads the file from the project root. For Cursor, copy it to `.cursor/mcp.json`; for VS Code, copy it to `.vscode/mcp.json` and rename the top-level key `mcpServers` to `servers`.

Two servers are available:

| Server | What the agent gets | Offered when |
|--------|---------------------|--------------|
| `cardano-debug` | Validates and step-debugs transactions and Plutus scripts before they are submitted: phase-1 and phase-2 validation, redeemer errors and traces, script decompilation, a UPLC debugger. Runs locally through `npx`; no API key needed. | always; selected by default |
| `yaci-devkit` | Drives the local devnet: status, faucet top-up, UTxOs, submit, reset. Served by Yaci DevKit itself while `just -f devnet/Justfile dev` runs. Needs Yaci DevKit 0.12.0-beta5 or later (`npm install -g @bloxbean/yaci-devkit@beta`); the stable release has no MCP endpoint, which is why this one is opt-in. | the devnet tool is `yaci`; opt-in |

Interactive setup lets you toggle them. In one-shot mode, pass [`--mcp <id>`](commands.md#create-a-project) to choose, or `--no-mcp` to skip the file. `cardano-init list` shows the same table.

API keys never go into the file. The `cardano-debug` entry passes `KOIOS_API_KEY` and `BLOCKFROST_PROJECT_ID_<NETWORK>` through from your shell with `${VAR:-}`, so set them there when the public Koios rate limit gets in the way. Claude Code expands that syntax; in a Cursor or VS Code copy, use `${env:VAR}` instead or remove the `env` block.

You can add servers of your own to the file. `add --mcp <id>` and `remove --mcp <id>` add or remove the servers above later on, and a role change adds or removes the ones tied to it; your own entries are never touched. The generated `AGENTS.md` explains each server to the agent.

## Changing the stack later

From inside the project, use [`add`](commands.md#add) and [`remove`](commands.md#remove) to add, replace, or remove components. `cardano-init` reads the current selection from the component directories (the project has no metadata file) and updates the shared top-level files.
